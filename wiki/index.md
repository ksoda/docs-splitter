## 実物PDFでの境界照合（確認日: 2026-09-23、実測）

- 事実: 正しい境界でも自動照合はほぼ一致しない。「最初の非空行 = タイトル」の判定では、O'Reilly書籍（340ページ、しおりから作った章境界）が0/17、Software Design誌が0/32と0/8だった。1行目は柱かページ番号（`v`、`xi`、`63`、`10 - Software Design`）になる。
- 事実: 日本語の文字化けはPDF側ではなくpypdfの抽出の限界だった。同じページを `pdftotext`（poppler、導入済み）で読むと正しい日本語が得られる。
- 事実: タイトルの先頭12字がページ本文に含まれるかで判定すると、書籍はpypdfで1/17、pdftotextで12/17だった。外れた5件（表紙・クレジット・原書大扉・権利表記・奥付）は、紙面にしおりのタイトルが印刷されていない。雑誌はしおりが区分名（■連載：Column など）のため、どちらの抽出でも0/8だった。
- 解釈: 現状の `review_items` は常に全境界になる。このため `REVIEW_REQUIRED` は、確認の要否を見分ける仕組みとして機能していない。
- 未決: 抽出器の変更、含有判定、照合不能という状態の追加は、「あいまい候補提示は初回スコープ外」という決定の変更にあたる。本人の判断を待つ。
- 根拠: [停止報告の訂正](../tasks/2026-09-23-software-design-split-stopped.md)。

## TOCの作り方（確認日: 2026-09-23）

- 事実: 対象の2冊とも、PDFにしおりがある（雑誌48件、書籍213件）。しおりには正しいPDFページが入っている。前セッションでは印刷目次を画像で読み、+10の補正を求めるのに約60分かかった。しおりを使えば数秒で済む。
- 事実: 画像から読んだタイトル32件のうち2件が誤読だった（実録→実践、魅惑→蝕蝕）。しおりか `pdftotext` と照合すれば防げた。
- 事実: 雑誌の `/PageLabels` は1〜205の連番で、紙面のノンブルとは一致しない。書籍はi〜xxxii、1〜308で紙面と一致する。
- 手順: しおりからTOC案を作る → 印刷目次と見比べて粒度を決める → 境界は `pdftotext` で確認し、テキストで確認できないページだけ `pdftoppm` で画像確認する。
- 出力の性質: 分割後の合計サイズは元の1.9〜2.5倍になる（フォントなどの共有リソースがファイルごとに複製されるためと推定。未検証）。

## 実行上の落とし穴（確認日: 2026-09-23）

- 事実: loop_guardの60分には権限承認の待ち時間も含まれる。前セッションは59分時点で承認が必要なコマンドを出し、承認の8分間で上限を超えた。
- 事実: `cmd 2>&1 | grep -v fontTools; echo $?` の `$?` はgrepの終了コードになる。CLIの出力が警告だけだとgrepが1を返し、成功を失敗と誤認した。
- 事実: 停止報告の内容が誤っていた。再開時は報告を鵜呑みにせず、transcript（`~/.claude/projects/<project>/<session>.jsonl`）と成果物の更新時刻で確かめる。
- 事実: 長いタイトル（UTF-8で約250バイト超）だと `write_unit_pdfs` が `OSError: File name too long` で落ちる。DomainErrorにならない（合成タイトルで再現、未修正）。
